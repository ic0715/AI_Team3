## 1. Purpose

**터치포인트**: AI 연동 #3 — 역량 방향 도출 (결정적 + 생성형)

**입력**: 사용자의 Top 5 강점(`strength_analyses.strengths`), 커리어 인터뷰 결과(`career_interview_results.key_insights` 7키 + `mentioned_competencies`, `ai_summary`), 그리고 정적 레퍼런스인 12역량 × 연계 강점 5개 매핑(`competency_action_map.md`).

**출력**:
- DB 저장: `career_interview_results.recommended_competencies` JSONB — 5개 옵션 카드 (`code` / `match_score` / `badge` / `slot`).
- DB 미저장: 5개 카드의 `personalized_text` (메모리/세션, p10 이동 후 폐기).

**역할**:
- Step 1 (코드, AI 미사용): `match_score` 계산 → 5개 슬롯 결정 → `recommended_competencies` 골격 생성.
- Step 2 (AI 1회 호출): 5개 카드 각각의 개인화 문구 생성 (DB 미저장).
- Step 3 (DB UPDATE): Step 1 결과만 `recommended_competencies`에 저장.

> 사용자가 5개 카드 중 1개를 선택하면 `goals` 테이블 INSERT로 흘러간다 (이 명세서 범위 외).

## 3. Persona & Voice

> Step 1은 코드 단계라 페르소나 N/A.
> 아래는 Step 2(AI 카드 문구 개인화)에만 적용된다.

**페르소나**: 사용자의 인터뷰를 함께 들은 직후의 커리어 코치. 카드 한 장씩, 짧고 또렷한 추천 메모를 남기는 톤.

**핵심 자세**:
- 카드 한 장의 `personalized_text`는 **2~3문장**, 80~140자 사이.
- 사용자의 인터뷰 표현을 **그대로 인용하거나 가까운 표현으로 되받는다** (echo-back).
- 강점은 직접 호명해도 좋다 — 카드 단계에서는 "분석 강점이 ~로 확장될 수 있어요" 같은 연결 표현이 자연스럽다.
- 단, 진단·평가하지 않는다 ("당신은 ~형 인재입니다" 금지).

**톤**:
- 존댓말, 따뜻하지만 정중. 카드 5장의 톤이 균질해야 한다 (특정 카드만 과하게 권유하거나 식는 일 없음).
- 한국어, 이모지·감탄사 자제, 마침표로 끝맺음.

**금지 표현**:
- "AI로서 말씀드리면…" / "분석 결과…"
- "정답은 ~입니다" / "~해야 합니다"
- 강점 페어 명칭이나 페어 컨텍스트 직접 인용 (이번 단계는 페어 컨텍스트를 입력으로 받지 않음)
- 다른 카드를 깎아내리는 표현 ("다른 옵션보다…")

**필수 표현 패턴**:
- 사용자 인터뷰 인용 한 조각 + 해당 역량이 그 흐름과 연결되는 이유 한 줄 + (선택) 해당 역량의 첫 한 걸음에 대한 가벼운 암시.
- `badge`별 톤 차이:
  - `strength_match` → "이미 가진 결과 잘 맞물려요" 류
  - `user_interest` → "직접 말씀하신 ~를 키우는 방향이에요" 류
  - `growth_potential` → "지금까지의 결과는 다른 결을 더해보는 방향이에요" 류

## 4. Logic / Pipeline

### 4.1 결정적 단계 (Step 1: 코드, AI 호출 없음)

**입력**:
- `top5_strengths`: Top 5 강점 한글명 리스트 5개 (예: `["성취", "분석", "체계", "집중", "전략"]`)
- `mentioned_competencies`: 1번 명세서 출력의 0~3개 코드 배열
- `COMPETENCIES`: 위 2.2의 12역량 매핑 상수

**처리 의사코드**:

```python
from itertools import combinations

# 0) 입력 정규화
top5_set = set(top5_strengths)             # {"성취", "분석", "체계", "집중", "전략"}
mentioned = list(mentioned_competencies)   # ["T-2", "I-2"] or []

# 1) 12역량 각각에 대해 match_score 계산
#    match_score = |Top 5 ∩ 역량 연계 강점 5개|  (0~5)
scored = []
for c in COMPETENCIES:
    score = len(top5_set & set(c["linked_strengths"]))
    scored.append({
        "code": c["code"],
        "domain": c["domain"],
        "match_score": score,
    })

# 2) 정렬 키
#    1순위: match_score 내림차순
#    2순위: 도메인 분포 (지금까지 채운 도메인 다양성 기여)
#    3순위: 코드 알파벳 순 (T-1 < T-2 < ... < E-3)
#
# tie-break의 "도메인 분포 우선"은 단계별로 적용 (아래 select_top3에서 처리).
def code_sort_key(item):
    return (-item["match_score"], item["code"])

scored.sort(key=code_sort_key)  # 1순위·3순위만 적용된 사전 정렬

# 3) 슬롯 1~3 채우기 — 결정적 매칭 상위 3개 (도메인 분포 우선)
def select_top3(scored):
    chosen = []
    used_domains = set()
    # (a) 1차 패스: match_score 내림차순으로 보되, 같은 점수 안에서는 새 도메인 우선
    grouped_by_score = {}
    for item in scored:
        grouped_by_score.setdefault(item["match_score"], []).append(item)
    for score in sorted(grouped_by_score.keys(), reverse=True):
        bucket = grouped_by_score[score]
        # 새 도메인 먼저
        new_domain = [b for b in bucket if b["domain"] not in used_domains]
        same_domain = [b for b in bucket if b["domain"] in used_domains]
        ordered = sorted(new_domain, key=lambda x: x["code"]) + \
                  sorted(same_domain, key=lambda x: x["code"])
        for item in ordered:
            if len(chosen) == 3:
                return chosen
            chosen.append(item)
            used_domains.add(item["domain"])
    return chosen

slots_1_2_3 = select_top3(scored)
chosen_codes = {s["code"] for s in slots_1_2_3}

# 4) 슬롯 4 — user_interest
#    mentioned_competencies 중 슬롯 1~3에 없는 첫 1개 → badge="user_interest"
#    fallback: mentioned가 비었거나 모두 슬롯 1~3과 중복이면
#             → 결정적 매칭 4위로 채움, badge="strength_match"
def pick_slot_4(scored, chosen_codes, mentioned):
    for code in mentioned:                    # 인터뷰에서 언급된 순서를 신뢰
        if code not in chosen_codes:
            entry = next(s for s in scored if s["code"] == code)
            return {**entry, "badge": "user_interest"}
    # fallback: 결정적 매칭 4위 (이미 chosen_codes에 없는 것 중 사전정렬 순서로)
    for entry in scored:
        if entry["code"] not in chosen_codes:
            return {**entry, "badge": "strength_match"}
    raise RuntimeError("12개 역량이 모두 슬롯 1~3에 들어간 경우는 없음")

slot_4 = pick_slot_4(scored, chosen_codes, mentioned)
chosen_codes.add(slot_4["code"])

# 5) 슬롯 5 — growth_potential
#    슬롯 1~4와 다른 도메인의 역량 중 match_score가 가장 높은 1개
#    fallback: 슬롯 1~4가 이미 4개 도메인 모두 커버하면
#             → 결정적 매칭 5위 (chosen 제외 다음 순서), badge="strength_match"
def pick_slot_5(scored, chosen_codes, slots_1_to_4):
    covered_domains = {s["domain"] for s in slots_1_to_4}
    if len(covered_domains) == 4:
        # 4개 도메인 다 커버 → fallback
        for entry in scored:
            if entry["code"] not in chosen_codes:
                return {**entry, "badge": "strength_match"}
        raise RuntimeError("불가능")
    # 다른 도메인의 역량 중 match_score 최대
    other_domain_pool = [
        e for e in scored
        if e["code"] not in chosen_codes and e["domain"] not in covered_domains
    ]
    # other_domain_pool은 이미 사전 정렬된 scored를 그대로 필터링한 결과이므로
    # match_score 내림차순, 같은 점수면 코드 알파벳 순으로 첫 항목 선택
    return {**other_domain_pool[0], "badge": "growth_potential"}

slots_1_to_4 = [
    {**slots_1_2_3[0], "badge": "strength_match"},
    {**slots_1_2_3[1], "badge": "strength_match"},
    {**slots_1_2_3[2], "badge": "strength_match"},
    slot_4,
]
slot_5 = pick_slot_5(scored, chosen_codes, slots_1_to_4)

# 6) 5개 슬롯 + slot index 부여
recommended = []
for i, s in enumerate(slots_1_to_4 + [slot_5], start=1):
    recommended.append({
        "code":        s["code"],
        "match_score": s["match_score"],
        "badge":       s["badge"],
        "slot":        i,
    })

# recommended는 이대로 Step 3에서 DB UPDATE에 사용된다.
# Step 2(AI 호출)에는 recommended를 입력으로 그대로 넘긴다.
```

**fallback 룰 요약** (결정사항 #6):

| 트리거 | 동작 |
| --- | --- |
| 슬롯 4: `mentioned_competencies = []` | 결정적 매칭 4위로 채움 → `badge="strength_match"` |
| 슬롯 4: `mentioned_competencies`가 모두 슬롯 1~3과 중복 | 결정적 매칭 4위로 채움 → `badge="strength_match"` |
| 슬롯 5: 슬롯 1~4가 이미 4개 도메인 모두 커버 | 결정적 매칭 5위로 채움 → `badge="strength_match"` |

> 즉, 정상 케이스에서는 `badge`가 `strength_match`(슬롯 1~3), `user_interest`(슬롯 4), `growth_potential`(슬롯 5)로 1:1:1:1:1 분포하지만, fallback 시 `strength_match` 비중이 4~5개로 늘어날 수 있다.

### 4.2 AI Prompt Template (Step 2: 카드 personalized_text 생성)

> 1회 호출. 5개 카드의 `personalized_text`를 한 번에 받는다 (개별 호출 5회보다 비용·일관성에서 유리).

#### 4.2.A System Prompt

```text
당신은 사용자의 커리어 인터뷰를 함께 들은 코치입니다.
지금부터 5개 역량 카드 각각에 대해, 사용자에게 보여줄 짧은 추천 메모를 작성합니다.
한국어로, 존댓말로, 따뜻하지만 정중하게 씁니다.

[원칙]
- 카드 1장당 personalized_text는 2~3문장, 80~140자.
- 사용자의 인터뷰에서 나온 표현을 한 조각 인용하거나 가까운 말로 되받습니다.
- 강점명은 직접 호명해도 됩니다 ("분석 강점이 ~로 확장될 수 있어요" 가능).
- 진단·평가하지 마세요 ("당신은 ~형 인재입니다" 금지).
- 다른 카드를 깎아내리지 마세요 ("다른 옵션보다…" 금지).
- "AI로서", "분석 결과", "데이터에 따르면" 금지.

[badge별 톤]
- strength_match: 이미 가진 강점이 이 역량과 어떻게 맞물리는지를 짧게 짚어줍니다.
- user_interest:  사용자가 인터뷰에서 직접 말한 흐름을 받아, 그 흐름이 이 역량으로 연결됨을 짚어줍니다.
- growth_potential: 지금까지의 결과와 결이 다르지만 시야를 넓혀볼 만하다는 톤. 부담 없이 권합니다.

[출력 형식 — 매우 중요]
다른 설명·서두·코드블록 없이 순수 JSON 객체 하나만 출력합니다.

{
  "cards": [
    { "slot": 1, "personalized_text": "..." },
    { "slot": 2, "personalized_text": "..." },
    { "slot": 3, "personalized_text": "..." },
    { "slot": 4, "personalized_text": "..." },
    { "slot": 5, "personalized_text": "..." }
  ]
}

각 personalized_text는 80자 이상 140자 이하의 한국어 텍스트입니다.

<사용자_프로필>
닉네임: {{nickname}}
직업/분야: {{job_field}}
경력 단계: {{career_level_label}}
</사용자_프로필>

<사용자_Top5_강점>

2위: {{strength_2.name_ko}} — {{strength_2.description}}
3위: {{strength_3.name_ko}} — {{strength_3.description}}
4위: {{strength_4.name_ko}} — {{strength_4.description}}

</사용자_Top5_강점>

<커리어_인터뷰_요약>

- 일에서 에너지: {{key_insights.current_satisfaction}}
- 답답한 순간:    {{key_insights.current_frustration}}
- 3~5년 비전:    {{key_insights.future_vision}}
- 일하는 방식:   {{key_insights.work_style}}
- 핵심 가치:      {{key_insights.values | join(", ")}}
```

#### 4.2.C Few-shot 예시 2: 엣지 케이스 — `mentioned_competencies = []`

**입력 컨텍스트 (요약)**:

**핵심 규칙**: 슬롯 4의 personalized_text도 **`strength_match` 톤**으로 써야 한다. "직접 말씀하신 ~"이라는 표현을 쓰면 안 됨 (사용자가 그 역량을 언급하지 않았으므로).


## 5. Output Schema

### 5.1 DB 저장 필드

**대상 컬럼**: `career_interview_results.recommended_competencies` (JSONB, nullable).
**저장 시점**: Step 1 완료 직후. Step 2의 `personalized_text`는 저장하지 않는다 (결정사항 #7).

**JSON Schema**:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "array",
  "minItems": 5,
  "maxItems": 5,
  "items": {
    "type": "object",
    "required": ["code", "match_score", "badge", "slot"],
    "additionalProperties": false,
    "properties": {
      "code": {
        "type": "string",
        "enum": [
          "T-1","T-2","T-3","I-1","I-2","I-3",
          "R-1","R-2","R-3","E-1","E-2","E-3"
        ]
      },
      "match_score": { "type": "integer", "minimum": 0, "maximum": 5 },
      "badge": {
        "type": "string",
        "enum": ["strength_match", "user_interest", "growth_potential"]
      },
      "slot": { "type": "integer", "minimum": 1, "maximum": 5 }
    }
  }
}
```

**추가 무결성 룰** (배열 차원, 코드로 검증):
- `slot` 값은 정확히 `[1, 2, 3, 4, 5]`로 하나씩 등장.
- `code` 값은 5개가 모두 distinct.
- `match_score`는 단조 증가하지 않을 수 있음 (슬롯 4·5는 룰에 따라 점수가 더 낮은 항목이 들어감).

**UPDATE 쿼리**:

```sql
UPDATE career_interview_results
   SET recommended_competencies = :recommended_jsonb
 WHERE id = :career_interview_id
   AND user_id = auth.uid();
```

> RLS: `career_interview_results` UPDATE는 `recommended_competencies` 컬럼만 허용 (spec-schema.md 7.RLS 주석 ¹). 앱이 다른 컬럼은 PATCH하지 않도록 제한.

### 5.2 화면 표시용 (DB 미저장)

**메모리 스키마** (브라우저 React state 등):

```typescript
type RecommendedCardForDisplay = {
  // DB 동일
  code: "T-1" | "T-2" | ... | "E-3";

  goal_title: string;        // 코드 → 한글명 매핑
```

## 6. Validation & Fallback

### 6.1 Step 1 출력 검증 (코드)

| 검증 항목 | 룰 | 위반 시 |
| --- | --- | --- |
| 길이 | 정확히 5개 | 코드 버그 — 예외 발생, 처음부터 재계산 |
| `slot` 분포 | `{1,2,3,4,5}` 일치 | 동일 |
| `code` 중복 없음 | `distinct count == 5` | 동일 |
| `match_score` 범위 | 0~5 정수 | 동일 |
| `badge` enum | 3종 중 하나 | 동일 |
| 슬롯 1~3 badge | 모두 `strength_match` | 동일 |
| 슬롯 4 badge | `user_interest` 또는 fallback `strength_match` | 동일 |
| 슬롯 5 badge | `growth_potential` 또는 fallback `strength_match` | 동일 |

> Step 1은 결정적 코드라 검증 실패는 사실상 코드 버그를 의미한다. 위반 시 사용자에게 "잠시 후 다시 시도해주세요"로 안내하고 클라이언트 에러 로그.

### 6.2 Step 2 출력 검증 (AI)

**파싱 단계**:

```python
# 1) JSON 파싱
data = json.loads(response_text)

# 2) 스키마 검증
assert "cards" in data
assert isinstance(data["cards"], list) and len(data["cards"]) == 5

slots_seen = set()
for card in data["cards"]:
    assert "slot" in card and "personalized_text" in card
    assert card["slot"] in {1, 2, 3, 4, 5}
    slots_seen.add(card["slot"])
    text = card["personalized_text"].strip()
    assert 60 <= len(text) <= 200    # 약간 여유 있게 검증

assert slots_seen == {1, 2, 3, 4, 5}
```

**검증 룰**:

| 검증 항목 | 룰 | 위반 시 |
| --- | --- | --- |
| JSON 파싱 | 유효한 JSON | 재시도 |
| `cards` 키 존재 + 5개 | required | 재시도 |
| 모든 카드에 `slot` + `personalized_text` | required | 재시도 |
| `slot` 분포 `{1,2,3,4,5}` | 일치 | 재시도 |
| `personalized_text` 길이 | 60~200자 (System Prompt는 80~140 권고지만 검증은 여유) | 60자 미만이면 재시도 / 200자 초과면 200자 자르기 |
| 텍스트 안전성 | 욕설·차별 표현 없음 (선택적 모더레이션) | 재시도 |

### 6.3 재시도 정책

**재시도 트리거 (Step 2)**:
- JSON 파싱 실패
- 필수 키 누락
- `slot` 분포 불일치
- 길이 60자 미만 카드 1장 이상

**재시도**: 최대 **2회**. 같은 input·system prompt로 재호출.

**2회 모두 실패 시 fallback**: AI 카드 문구를 포기하고 **정적 fallback 텍스트**를 5개 카드 각각의 `badge`별로 사용.

```python
FALLBACK_TEXTS = {
  "strength_match":   "당신의 강점과 자연스럽게 연결되는 방향이에요. 12주 동안 한 걸음씩 다져볼 수 있어요.",
  "user_interest":    "인터뷰 중에 자연스럽게 떠올랐던 결을 키우는 방향이에요. 12주의 출발점으로 잘 맞아요.",
  "growth_potential": "지금까지와 결이 조금 다르지만 시야를 넓혀볼 만한 방향이에요. 가볍게 시작해볼 수 있어요.",
}
```

> Step 1 결과는 정상 저장되므로, Step 2 fallback은 화면 카드 문구만 정적 텍스트로 떨어진다. 서비스 흐름 단절 없음.

### 6.4 Step 1 fallback 룰 (재확인, 결정사항 #6)

위 4.1에 코드로 명시. 요약:

| 슬롯 | 정상 | fallback |
| --- | --- | --- |
| 1~3 | 결정적 매칭 상위 3 | (없음 — 항상 정상) |
| 4 | mentioned 첫 1개 → user_interest | mentioned 빈 배열·중복 시 → 결정적 매칭 4위 → strength_match |
| 5 | 다른 도메인 최고점 → growth_potential | 슬롯 1~4가 4도메인 다 커버 → 결정적 매칭 5위 → strength_match |

## 7. Edge Cases

| # | 케이스 | 처리 |
| --- | --- | --- |
| 1 | `strength_analyses` 레코드가 없음 | 인터뷰 진입 단계에서 가드되었어야 함. Step 1 진입 시점에 다시 가드: 강점 분석 화면으로 강제 리다이렉트, AI 호출 없음 |
| 2 | `career_interview_results` 레코드가 없음 | 동일 — 커리어 인터뷰 화면(p08)으로 리다이렉트 |
| 3 | Top 5 강점 한글명이 정규명과 미세하게 다름 (예: "지적 사고" vs "지적사고") | 정규화 함수로 공백·중점 제거 후 비교. 매핑 실패 시 해당 강점은 매칭에서 제외 (조용히 0점 처리) |
| 4 | `mentioned_competencies`에 4개 이상이 들어있음 | 1번 명세서 검증 단계에서 이미 3개로 잘렸을 것. Step 1은 그대로 신뢰하고 처음 3개만 사용 |
| 5 | `mentioned_competencies`에 enum 외 코드 (예: "T-4") | 1번 명세서 검증에서 제거됐을 것. Step 1에서도 한 번 더 필터링 후 진행 |
| 6 | 모든 12역량의 `match_score`가 0 (Top 5와 어느 매핑도 겹치지 않음) | 슬롯 1~3은 코드 알파벳 순(`E-1`, `E-2`, `E-3`)으로 채워짐. 슬롯 4·5도 정상 룰 적용. 카드 문구는 `strength_match` 톤이 다소 어색해질 수 있으나 fallback 텍스트로도 보완됨 |
| 7 | Step 1 결과 슬롯 4가 슬롯 1~3과 같은 도메인 | 정상 — 슬롯 4는 사용자 의도이므로 도메인 분포 룰 적용 안 함. 슬롯 5의 도메인 분포 판단에는 그대로 반영됨 |
| 8 | 슬롯 5 fallback 시 슬롯 5의 `match_score`가 슬롯 4의 `match_score`보다 높음 | 정상. `match_score`는 슬롯 순서를 결정하는 정렬 기준이 아니라 표시용 메타데이터일 뿐이다 |
| 9 | Step 2 AI 호출 타임아웃 | 6.3 fallback. 정적 텍스트로 카드 5장 채워서 화면 진행 |
| 10 | Step 2 출력 중 일부 카드만 60자 미만 | 전체 재시도 (개별 카드 패치보다 일관성 유지가 우선) |
| 11 | 사용자가 같은 인터뷰에 대해 두 번 이상 "역량 방향 받기" 버튼 클릭 | `recommended_competencies` UPDATE는 idempotent. Step 1·2를 다시 실행해 덮어씀. 다만 `personalized_text`는 매번 다르게 나올 수 있음 (DB 미저장이므로 무관) |
| 12 | `goal_title` lookup 실패 (앱 상수에 코드 누락) | 클라이언트 빌드 에러 — 배포 전 차단되어야 함. 런타임에 만나면 카드에 `code` 자체를 표시하고 에러 로그 |
