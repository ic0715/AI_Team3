## 1. Purpose

**터치포인트**: AI 연동 #3 — 역량 방향 도출 (결정적 + 생성형)

**입력**: 사용자의 Top 5 강점(`strength_analyses.strengths`), 커리어 인터뷰 결과(`career_interview_results.key_insights` 7키 + `growth_competencies`, `ai_summary`), 그리고 정적 레퍼런스인 12역량 × 연계 강점 5개 매핑(`competency_action_map.md`).

**출력**:
- DB 저장: `career_interview_results.recommended_competencies` JSONB — 5개 옵션 카드 (`code` / `match_score` / `badge` / `slot`).
- DB 미저장: 5개 카드의 `personalized_text` (메모리/세션, p10 이동 후 폐기).

**역할**:
- Step 1 (코드, AI 미사용): 성장 의도(`growth_competencies`) 우선 + 부족분 강점 보충 → 5개 슬롯 결정 → `recommended_competencies` 골격 생성.
- Step 2 (AI 1회 호출): 5개 카드 각각의 개인화 문구 생성 (DB 미저장).
- Step 3 (DB UPDATE): Step 1 결과만 `recommended_competencies`에 저장.

> 사용자가 5개 카드 중 1개를 선택하면 `goals` 테이블 INSERT로 흘러간다 (이 명세서 범위 외).

## 3. Persona & Voice

> Step 1은 코드 단계라 페르소나 N/A.
> 아래는 Step 2(AI 카드 문구 개인화)에만 적용된다.

**페르소나**: 사용자의 인터뷰를 함께 들은 직후의 커리어 코치. 카드 한 장씩, 짧고 또렷한 추천 메모를 남기는 톤.

**핵심 자세**:
- 카드 한 장의 `personalized_text`는 **2~3문장**, 80~140자 사이.
- 사용자의 인터뷰 표현을 **그대로 인용하거나 가까운 표현으로 되받는다** (echo-back).
- 강점은 직접 호명해도 좋다 — 카드 단계에서는 "분석 강점이 ~로 확장될 수 있어요" 같은 연결 표현이 자연스럽다.
- 단, 진단·평가하지 않는다 ("당신은 ~형 인재입니다" 금지).

**톤**:
- 존댓말, 따뜻하지만 정중. 카드 5장의 톤이 균질해야 한다 (특정 카드만 과하게 권유하거나 식는 일 없음).
- 한국어, 이모지·감탄사 자제, 마침표로 끝맺음.

**금지 표현**:
- "AI로서 말씀드리면…" / "분석 결과…"
- "정답은 ~입니다" / "~해야 합니다"
- 강점 페어 명칭이나 페어 컨텍스트 직접 인용 (이번 단계는 페어 컨텍스트를 입력으로 받지 않음)
- 다른 카드를 깎아내리는 표현 ("다른 옵션보다…")

**필수 표현 패턴**:
- 사용자 인터뷰 인용 한 조각 + 해당 역량이 그 흐름과 연결되는 이유 한 줄 + (선택) 해당 역량의 첫 한 걸음에 대한 가벼운 암시.
- `badge`별 톤 차이:
  - `user_interest` (기르고 싶은 역량) → "기르고 싶다고 하신/답답해하시던 ~를 키우는 방향이에요" 류. 사용자가 직접 말한 경우엔 그 표현을 되받고, gap에서 추론된 경우엔 그 답답함·목표와 연결한다.
  - `strength_match` (강점 보충 카드) → "이미 가진 강점과 잘 맞물려요" 류. 의도 신호가 부족해 강점 연계로 제안되는 카드.
  - `growth_potential` (레거시) → 신규 로직에서는 생성되지 않음. 구 데이터 렌더 시 "지금까지와 다른 결을 더해보는 방향" 톤.

## 4. Logic / Pipeline

### 4.1 결정적 단계 (Step 1: 코드, AI 호출 없음)

**설계 원칙 (v1.0 — 의도 우선)**: "무엇을 기를지"는 **인터뷰에서 추출한 성장 의도(`growth_competencies`)**가 결정한다. 강점(`match_score`)은 선택을 주도하지 않고, 의도가 부족한 슬롯을 **보충**하는 데만 쓰인다. 강점의 본래 역할(이미 잘하는 것을 활용)은 다음 단계인 액션 아이템 도출에서 발휘된다.

**입력**:
- `top5_strengths`: Top 5 강점 한글명 리스트 5개 (예: `["성취", "분석", "체계", "집중", "전략"]`)
- `growth_competencies`: 1번 명세서 출력의 0~5개 코드 배열, **우선순위 순**
- `COMPETENCIES`: 위 2.2의 12역량 매핑 상수

**처리 의사코드**:

```python
# 0) 입력 정규화
top5_set = set(top5_strengths)
growth = list(growth_competencies)         # ["T-1", "I-3"] — 우선순위 순, 0~5개

# 1) 12역량 각각에 대해 match_score 계산 (보충 정렬용)
#    match_score = |Top 5 ∩ 역량 연계 강점 5개|  (0~5)
scored = []
for c in COMPETENCIES:
    score = len(top5_set & set(c["linked_strengths"]))
    scored.append({"code": c["code"], "domain": c["domain"], "match_score": score})

by_code = {s["code"]: s for s in scored}

# 강점 점수 내림차순, 동점 시 코드 알파벳 순 (보충용 사전 정렬)
strength_sorted = sorted(scored, key=lambda s: (-s["match_score"], s["code"]))

chosen, chosen_codes, used_domains = [], set(), set()

# 2) 의도 우선: growth_competencies 우선순위 순으로 슬롯을 채운다 (badge="user_interest")
for code in growth:
    if len(chosen) == 5:
        break
    item = by_code.get(code)
    if item is None or code in chosen_codes:
        continue
    chosen.append({**item, "badge": "user_interest"})
    chosen_codes.add(code)
    used_domains.add(item["domain"])

# 3) 부족분 강점 보충: 강점 점수 최고 + 새 도메인 우선 (다양성), badge="strength_match"
while len(chosen) < 5:
    remaining = [s for s in strength_sorted if s["code"] not in chosen_codes]
    if not remaining:
        break
    fresh = [s for s in remaining if s["domain"] not in used_domains]
    pick = (fresh or remaining)[0]            # strength_sorted가 점수 내림차순이므로 첫 항목이 최고점
    chosen.append({**pick, "badge": "strength_match"})
    chosen_codes.add(pick["code"])
    used_domains.add(pick["domain"])

# 4) slot index 부여 (의도 카드가 앞 슬롯 → 화면 상단 우선 노출)
recommended = [
    {"code": s["code"], "match_score": s["match_score"], "badge": s["badge"], "slot": i}
    for i, s in enumerate(chosen, start=1)
]
# recommended는 Step 3에서 DB UPDATE에 쓰이고, Step 2(AI 호출)에 그대로 넘어간다.
```

**슬롯 구성 요약**:

| 상황 | 결과 |
| --- | --- |
| `growth_competencies` 5개 이상 | 5장 전부 의도 기반(`user_interest`) — 강점 보충 0장 |
| `growth_competencies` k개 (0<k<5) | 앞 k장 의도(`user_interest`) + 나머지 (5−k)장 강점 보충(`strength_match`) |
| `growth_competencies = []` | 5장 전부 강점 보충(`strength_match`) — 안전한 fallback |

> 의도 카드는 항상 강점 보충 카드보다 앞 슬롯(화면 상단)에 온다. `growth_potential` 배지는 v1.0 선택 로직에서 더 이상 생성되지 않으며, 과거 저장 데이터 렌더 호환용으로만 타입에 남는다.

#### 4.2.B Few-shot 예시 1: 일반 케이스

**입력 컨텍스트 (요약)**:

```text

Top 5: 성취, 분석, 체계, 집중, 전략

  - 꿈: ""
```

#### 4.2.C Few-shot 예시 2: 엣지 케이스 — `growth_competencies = []`

**입력 컨텍스트 (요약)**:

## 5. Output Schema

### 5.1 DB 저장 필드

**대상 컬럼**: `career_interview_results.recommended_competencies` (JSONB, nullable).
**저장 시점**: Step 1 완료 직후. Step 2의 `personalized_text`는 저장하지 않는다 (결정사항 #7).

**JSON Schema**:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "array",
  "minItems": 5,
  "maxItems": 5,
  "items": {
    "type": "object",
    "required": ["code", "match_score", "badge", "slot"],
    "additionalProperties": false,
    "properties": {
      "code": {
        "type": "string",
        "enum": [
          "T-1","T-2","T-3","I-1","I-2","I-3",
          "R-1","R-2","R-3","E-1","E-2","E-3"
        ]
      },
      "match_score": { "type": "integer", "minimum": 0, "maximum": 5 },
      "badge": {
        "type": "string",
        "enum": ["strength_match", "user_interest", "growth_potential"]
      },
      "slot": { "type": "integer", "minimum": 1, "maximum": 5 }
    }
  }
}
```

**추가 무결성 룰** (배열 차원, 코드로 검증):
- `slot` 값은 정확히 `[1, 2, 3, 4, 5]`로 하나씩 등장.
- `code` 값은 5개가 모두 distinct.
- `match_score`는 단조 증가하지 않을 수 있음 (슬롯 4·5는 룰에 따라 점수가 더 낮은 항목이 들어감).

**UPDATE 쿼리**:

```sql
UPDATE career_interview_results
   SET recommended_competencies = :recommended_jsonb
 WHERE id = :career_interview_id
   AND user_id = auth.uid();
```

> RLS: `career_interview_results` UPDATE는 `recommended_competencies` 컬럼만 허용 (spec-schema.md 7.RLS 주석 ¹). 앱이 다른 컬럼은 PATCH하지 않도록 제한.

### 5.2 화면 표시용 (DB 미저장)

**메모리 스키마** (브라우저 React state 등):

```typescript

  code: "T-1" | "T-2" | ... | "E-3";
```

## 6. Validation & Fallback

### 6.1 Step 1 출력 검증 (코드)

| 검증 항목 | 룰 | 위반 시 |
| --- | --- | --- |
| 길이 | 정확히 5개 | 코드 버그 — 예외 발생, 처음부터 재계산 |
| `slot` 분포 | `{1,2,3,4,5}` 일치 | 동일 |
| `code` 중복 없음 | `distinct count == 5` | 동일 |
| `match_score` 범위 | 0~5 정수 | 동일 |
| `badge` enum | 3종 중 하나 | 동일 |
| 앞쪽 슬롯 badge | 의도 개수 k장은 `user_interest` (k=0~5) | 동일 |
| 뒤쪽 슬롯 badge | 나머지 (5−k)장은 `strength_match` | 동일 |
| badge 순서 | `user_interest`들이 `strength_match`들보다 앞 슬롯 | 동일 |

> Step 1은 결정적 코드라 검증 실패는 사실상 코드 버그를 의미한다. 위반 시 사용자에게 "잠시 후 다시 시도해주세요"로 안내하고 클라이언트 에러 로그.

### 6.2 Step 2 출력 검증 (AI)

**파싱 단계**:

```python
# 1) JSON 파싱
data = json.loads(response_text)

# 2) 스키마 검증
assert "cards" in data
assert isinstance(data["cards"], list) and len(data["cards"]) == 5

slots_seen = set()
for card in data["cards"]:
    assert "slot" in card and "personalized_text" in card
    assert card["slot"] in {1, 2, 3, 4, 5}
    slots_seen.add(card["slot"])
    text = card["personalized_text"].strip()
    assert 60 <= len(text) <= 200    # 약간 여유 있게 검증

assert slots_seen == {1, 2, 3, 4, 5}
```

**검증 룰**:

| 검증 항목 | 룰 | 위반 시 |
| --- | --- | --- |
| JSON 파싱 | 유효한 JSON | 재시도 |
| `cards` 키 존재 + 5개 | required | 재시도 |
| 모든 카드에 `slot` + `personalized_text` | required | 재시도 |
| `slot` 분포 `{1,2,3,4,5}` | 일치 | 재시도 |
| `personalized_text` 길이 | 60~200자 (System Prompt는 80~140 권고지만 검증은 여유) | 60자 미만이면 재시도 / 200자 초과면 200자 자르기 |
| 텍스트 안전성 | 욕설·차별 표현 없음 (선택적 모더레이션) | 재시도 |

### 6.3 재시도 정책

**재시도 트리거 (Step 2)**:
- JSON 파싱 실패
- 필수 키 누락
- `slot` 분포 불일치
- 길이 60자 미만 카드 1장 이상

**재시도**: 최대 **2회**. 같은 input·system prompt로 재호출.

**2회 모두 실패 시 fallback**: AI 카드 문구를 포기하고 **정적 fallback 텍스트**를 5개 카드 각각의 `badge`별로 사용.

```python
FALLBACK_TEXTS = {
  "strength_match":   "당신의 강점과 자연스럽게 연결되는 방향이에요. 12주 동안 한 걸음씩 다져볼 수 있어요.",
  "user_interest":    "인터뷰 중에 자연스럽게 떠올랐던 결을 키우는 방향이에요. 12주의 출발점으로 잘 맞아요.",
  "growth_potential": "지금까지와 결이 조금 다르지만 시야를 넓혀볼 만한 방향이에요. 가볍게 시작해볼 수 있어요.",
}
```

> Step 1 결과는 정상 저장되므로, Step 2 fallback은 화면 카드 문구만 정적 텍스트로 떨어진다. 서비스 흐름 단절 없음.

### 6.4 Step 1 fallback 룰 (재확인, v1.0 — 의도 우선)

위 4.1에 코드로 명시. 요약:

| 상황 | 슬롯 구성 |
| --- | --- |
| `growth_competencies` k개 (0<k≤5) | 앞 k장 의도(`user_interest`) + 나머지 (5−k)장 강점 보충(`strength_match`) |
| `growth_competencies = []` | 5장 전부 강점 보충(`strength_match`) — 안전한 fallback |
| 강점 보충 정렬 | 강점 점수 내림차순 1순위, 도메인 분산은 같은 점수 안에서만 타이브레이커 |

> `growth_potential` 배지는 v1.0 선택 로직에서 생성되지 않는다 (과거 데이터 렌더 호환용으로만 타입에 잔존).

## 7. Edge Cases

| # | 케이스 | 처리 |
| --- | --- | --- |
| 1 | `strength_analyses` 레코드가 없음 | 인터뷰 진입 단계에서 가드되었어야 함. Step 1 진입 시점에 다시 가드: 강점 분석 화면으로 강제 리다이렉트, AI 호출 없음 |
| 2 | `career_interview_results` 레코드가 없음 | 동일 — 커리어 인터뷰 화면(p08)으로 리다이렉트 |
| 3 | Top 5 강점 한글명이 정규명과 미세하게 다름 (예: "지적 사고" vs "지적사고") | 정규화 함수로 공백·중점 제거 후 비교. 매핑 실패 시 해당 강점은 매칭에서 제외 (조용히 0점 처리) |
| 4 | `growth_competencies`에 6개 이상이 들어있음 | 1번 명세서 검증 단계에서 이미 5개로 잘렸을 것. Step 1은 그대로 신뢰하고 앞 5개(우선순위 순)만 사용 |
| 5 | `growth_competencies`에 enum 외 코드 (예: "T-4") | 1번 명세서 검증에서 제거됐을 것. Step 1에서도 한 번 더 필터링(`by_code` 미존재 시 skip) 후 진행 |
| 6 | 모든 12역량의 `match_score`가 0 (Top 5와 어느 매핑도 겹치지 않음) | 강점 보충 슬롯이 코드 알파벳 순으로 채워짐. 의도 카드는 영향 없음. 강점 보충 카드 문구는 `strength_match` 톤이 다소 어색해질 수 있으나 fallback 텍스트로 보완됨 |
| 7 | 의도 카드들이 같은 도메인에 몰림 (예: 의도가 전부 T 도메인) | 정상 — 의도는 사용자 우선순위를 그대로 따르므로 도메인 분산 룰을 적용하지 않는다. 도메인 다양성은 강점 보충 슬롯에서만 고려 |
| 8 | 강점 보충 카드의 `match_score`가 앞쪽 의도 카드보다 높음 | 정상. 슬롯 순서는 의도 우선이지 점수 순이 아니다. `match_score`는 표시/디버그용 메타데이터일 뿐 |
| 9 | Step 2 AI 호출 타임아웃 | 6.3 fallback. 정적 텍스트로 카드 5장 채워서 화면 진행 |
| 10 | Step 2 출력 중 일부 카드만 60자 미만 | 전체 재시도 (개별 카드 패치보다 일관성 유지가 우선) |
| 11 | 사용자가 같은 인터뷰에 대해 두 번 이상 "역량 방향 받기" 버튼 클릭 | `recommended_competencies` UPDATE는 idempotent. Step 1·2를 다시 실행해 덮어씀. 다만 `personalized_text`는 매번 다르게 나올 수 있음 (DB 미저장이므로 무관) |
| 12 | `goal_title` lookup 실패 (앱 상수에 코드 누락) | 클라이언트 빌드 에러 — 배포 전 차단되어야 함. 런타임에 만나면 카드에 `code` 자체를 표시하고 에러 로그 |

**슬롯 1~2 선정** (의도 우선, `growth_competencies = ["T-2", "I-2"]`):
- 1순위 `T-2`(데이터 분석 능력 기르기) → 슬롯 1 (match=2, badge=`user_interest`)

**슬롯 3~5 선정** (강점 보충 — 강점 점수가 1순위, 도메인 분산은 같은 점수 안에서만):
- 남은 후보를 점수 내림차순으로: 점수3 `{E-3, T-3}`, 점수2 `{E-1, E-2, T-1}`(T-2는 사용), 나머지 0점.
- 슬롯 3: 점수3 그룹에서 새 도메인 우선 → `E-3`(E, 새 도메인) 채택. 사용 도메인 `{T, I, E}`.
- 슬롯 4: 점수3 그룹 잔여 `T-3`(T, 이미 사용) — 같은 점수 그룹 안에 새 도메인 없음 → 코드 순 `T-3` 채택. (점수2로 내려가지 않는다 — 점수가 도메인 분산보다 우선)

→ 슬롯 3: `E-3` (match=3), 슬롯 4: `T-3` (match=3), 슬롯 5: `E-1` (match=2)
